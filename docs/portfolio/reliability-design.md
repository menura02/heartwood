# Terminal client reliability design

11 November 2026

- Opening live chat captures the processed Matrix `next_batch` cursor. The first backward page and forward reads start from the same boundary. Each refresh processes `/sync` and at most one forward `/messages` page in sequence. An empty page advances when it has a valid continuation cursor. A cursor that fails to advance produces an error. A failed read preserves the previous position. Recent event IDs and encrypted events awaiting decryption use bounded memory. History commands maintain their own backward pagination cursors. [Matrix sync and pagination](https://spec.matrix.org/latest/client-server-api/#syncing)
- Each logical send uses one UUID and a Megolm payload generated once. An uncertain outcome leaves at most one pending transaction per room. `/retry` uses the original HTTP path and payload in the same process, session and device. The client first checks room rules, blocking, the current device and the original recipient ID. A definite server rejection on the first attempt has its own status. A later rejection leaves any earlier uncertain outcome unresolved. The server confirms acceptance with an event ID. [Matrix transaction IDs](https://spec.matrix.org/latest/client-server-api/#transaction-identifiers)
- `/conversations` lists accessible Heartwood rooms, peers and device trust status. A room and peer that stay in consecutive lists keep their number. A number that drops out of the list is retired. Heartwood checks the room and peer again when opening a chat and sending in live chat.
- Profile concurrency uses the file lock released by the operating system through Node 24's built-in SQLite. Profile writes remain atomic. The `in-use` directory prevents concurrent access with older clients. The client takes over a directory marked by the current lock protocol only after acquiring the SQLite lock. It stops for ambiguous or unmarked legacy directories. The ownership decision is independent of process IDs.
- The disposable loopback Synapse 1.164.2 lab uses the existing YAML files. The integration runner uses a separate test port and a temporary registration token. It starts the lab, checks its health, runs the test, and shuts it down in one run. Windows and Linux verification use the same lockfile and tracked test helpers. [CI workflow](../../.github/workflows/terminal.yml)

The room model, device pins and cryptography follow the existing threat model. Live receive and retry state last for the process lifetime. Operating system and filesystem locking guarantees apply to local storage.
